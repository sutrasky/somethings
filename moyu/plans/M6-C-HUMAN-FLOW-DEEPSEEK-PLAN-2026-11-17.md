## 第一步　保护迁移回滚（PR #48，Issue #37）

**故障位置。** `packages/db/migrations/rollback/0014_execution_reservations.down.sql` 在删除执行预留表前只检查目标哈希恰好出现一次。账本中已有后继迁移时仍可能删掉表和 0014 记录。迁移器随后按最新记录继续，无法补建这张表。当前测试先按顺序撤回所有后继迁移，绕过了故障条件。

**改法。** 在同一事务、首个 DDL 之前，按迁移器使用的账本顺序验证 0014 唯一且为最新。沿用内置哈希和普通 PostgreSQL 客户端可执行的纯 SQL。与迁移执行协调锁定账本，使校验到删除期间不能插入后继记录。

**验收。** 在一次性真实 PostgreSQL 中先保留后继记录并直接请求撤回 0014，记录修前行为。修后必须报错，逐项比较表、外键及账本前后快照。再验哈希不符、目标缺失、重复记录、重复回滚均拒绝。最后按合法顺序撤到 0014、回滚并重迁，核对表和约束恢复。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/37)

## 第二步　建好隔离验收环境，修复实例生命周期

### PR #49（Issue #36）　测试身份与特权文件

**故障位置。** M6-C 已支持每仓库运行身份，但旧矩阵的 `scripts/m5b/matrix/prepare-nonroot.sh` 仍授予共享配置写权限并复制宿主凭据。`stack.sh` 混用特权引导和测试身份可写目录。以 #36 和 #49 实际文件差异为准，PR 正文还混有 #58 的检查子进程说明。

**改法。** 复用每仓库身份，为探测仓配置独立凭据。特权配置及其父目录由受信身份管理，测试运行目录中的创建、更新和清理交给低权身份。预检只读，分别报告文件所有权、有效权限和授权仓范围。

**验收。** 在专用环境连跑两轮初始化、异常退出、清理和重新启动。核对宿主哨兵文件的内容、所有者和权限始终一致，测试身份只能写自己的目录。用专用身份验证指定探测仓的所需权限及对另一个受控私有仓的访问拒绝。授权尚未配齐时记录具体缺项，待现场项目保持待验。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/36)

### PR #53（Issue #41）　空目录启动、重启与进程归属

**故障位置。** 当前 M6-C unit 已配置 systemd 委托，死 PID 的卡槽也有过修复。但 supervisor 的 `process.ts` 在创建缺失根目录前尝试启用控制器。`manager.ts` 的死进程收尾可仅凭主 PID 消失清空实例归属，后代仍活、目录被复用等场景需要单独处理。

**改法。** 在现有委托边界内创建根目录、启用控制器，并在启动前验证实例组的计量文件。复用已有停止证明的 inode 校验，绑定实例代次、cgroup 对象和 PID 启动时间。停止、重启对账、休眠统一按归属证据处理。确认受管树为空才释放容量。仍有可确认的成员时按原代次接管或停止，归属未知时保留占位并说明原因。

**验收。** 在隔离 Linux unit 下从空目录冷启，依次测休眠、唤醒、supervisor 重启、主 PID 已退出但后代仍活、同名目录被重建、陌生进程占端口。记录每代 PID、inode、递归成员、端口、租约及执行槽。确认陌生进程未受影响，清理完成后下一实例确实能启动。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/41)

## 第三步　修复调度器重启和拒绝接单时的对账

### PR #50（Issue #39）　中断后正确接续执行回合

**故障位置。** 打断运行中的回合后，Bridge 可能在同一租约内生成新 assignment。`dispatcher/src/reservations.ts` 认领时要求 assignment 完全匹配，`sync.ts` 恢复时仍以旧预留行核对快照，可能持续写入 `snapshot_mismatch`。另有一条独立验收缺口，真实开放 PR 在两库重启期间能否保持待审阅。

**改法。** 在租约与预留行的同一事务中，对照当前 ticket、租约、fencing token 和权威运行时记录，确认后继回合后才更新预留。记下旧、新 assignment 和来源事件。迟到的旧回合与重放事件均不能把预留改回去。继续支持既有预留键。

**验收。** 先用真实 PG 注入新旧回合交错和重复事件，断言只发生一次有效接续。再在隔离栈打断任务，重启 Bridge、dispatcher 和两库，追加真实消息，确认输入已读、游标推进且只有一个 worker。另用真实开放 PR 验证重启前后 ticket 与 PR 关联一致、无自动开工，关闭 PR 后正常结票。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/39)

### PR #51（Issue #38）　只释放被拒接单的那一代租约

**故障位置。** 早先未接单会一直占用同仓执行槽。现基线已修正常释放和历史占位回收，#82 又加入返修转交。剩余缺口在 `sync.ts` 的 `applyIgnoredDecision` 与 `recoverIgnoredLeases`：按任务 holder 查找活动租约仍不足以证明拒绝回执对应这一次执行，预留记录也需要一起结清。

**改法。** 从回执点名的消息追溯其投递时绑定的租约 ID 和 fencing token。锁定并比对当前代次，有证据证明未开工时，原子结清预留、租约及任务绑定。已认领、仍有在途操作或旧记录缺少证明时保留占位，显示恢复原因。普通拒绝和 routed 转交共用代次校验，保留 #82 的交接和中文通知。

**验收。** 真实 PG 覆盖同任务新旧代次、迟到与重复拒绝、并发接管、历史记录和已运行 worker。再用真实 Bridge 验证普通拒绝后同仓下一任务实际启动，旧回执不关闭新任务、不释放新租约。返修转交仍更新同一 PR，源会话仅收到一次完成通知。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/38) · [已合入的 #82](https://github.com/bouyer-sutrasky/MoYu/pull/82)

## 第四步　补齐暂停超时的恢复路径（PR #55，Issue #47）

**故障位置。** `0024-pause-before-start.patch` 在启动中止超时时记录 pauseFailed，平台可进入 blocked，普通 resume 又要求 stopped。旧 PR 选择记录此边界。本计划建议补可恢复出口。旧矩阵脚本还会从命令参数传令牌，暂停或恢复被拒后继续执行，退出码不能可靠反映失败。

**改法。** 先固定超时用例，再允许对同一暂停操作重新核对停止状态。使用当前 ticket、操作及租约代次绑定的证据。确认已停后原子结清原操作并允许恢复，未确认时保持占位并显示下一步。修订 M4 执行控制文档，写清尚无 assignment 时如何识别暂停。脚本从受限输入读取凭据，关键断言失败返回非零，记录实际加载制品的哈希。

**验收。** 分别在启动前、启动中、启动后暂停。强制启动中止超时，验证无法误报已停，在取得停止证明后可从原任务恢复。重复请求只生成一次有效恢复。Web 和另一 GitHub 身份发起的真实提及各跑一次，核对停止证据、租约和 worker 数。故意使断言失败，确认脚本退出非零且日志无凭据。[原 PR](https://github.com/bouyer-sutrasky/MoYu/pull/55)

## 第五步　补两项现场验收，按失败结果决定是否改代码

### PR #52（Issue #40）　同一工作从两个入口到达

当前已有数据库唯一约束、导入重放和重复 ticket 暂停测试。缺少的是从两个真实入口发起同一工作时的实际执行次数。使用探测仓、Web 所有者会话和独立 GitHub 发送者，分别跑 Web 先、GitHub 先、并发到达与事件重放。逐条关联入口消息、ticket、assignment、租约、worker 启动和实际 PR 写入。每个场景只允许一次有效执行及一份预期外部变更。若出现重复，定位首次分叉的位置，再修该入口的同仓需求认领或副作用幂等，重跑全部顺序。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/40)

### PR #54（Issue #42）　聚合 8 GiB 边界与内存等待恢复

当前切片配置和 supervisor 已实现硬上限与迟滞。旧矩阵实际触及过 4 GiB 硬边界，全栈压力记录约到 6.19 GiB；按执行名额排队的实测也不能验证内存迟滞。复用 #54 的有界预检，在独立 Linux 切片核对成员、实效上限、宿主余量与清理条件。分别记录节流、成员级 OOM 和切片硬上限的计数及作用域。另保持执行名额可用，仅以内存压力令候选仓进入 resource_wait，再降低压力，观察跨过迟滞阈值后的实际启动。验收须有 memory.current、peak、events.local、宿主余量和等待原因的同一时间线，确认无抢占、无异常残留。预检不满足时保留未验记录。[原 Issue](https://github.com/bouyer-sutrasky/MoYu/issues/42)

## 每项交付流程

1. 固定最新 main SHA 和实际运行制品。以原 Issue 的失败条件建立基线，保存命令、退出码与状态快照。补验项若首次运行即通过，直接提交证据。
2. 对复现的缺陷做最小修改，用同一输入重跑，并覆盖该项列出的重复、迟到、并发或重启边界。运行 `pnpm check` 和 `pnpm test:integration`。涉及上游的改动通过 MoYu 集成补丁提交，并验证补丁可应用、构建及契约测试通过。
3. 在独立 PR 附修前与修后结果、完整提交 SHA、制品哈希、脱敏现场记录和未验项。数据库变更附隔离回滚与重迁结果，服务改动附回退方法。待对应现场判据及必需 CI 通过后再合并，并在原 Issue 关联替代 PR。
